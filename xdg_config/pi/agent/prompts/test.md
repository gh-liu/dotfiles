Design, add, and run discriminating tests for the target changes, prioritizing untested behaviors, missing edge cases, or failing checks from the current discussion and incorporating any custom instructions below.

Target, scope, or custom instructions: ${@:-none}

1. **Resolve target, identify gaps & choose test layer**:
   - If the input specifies a target (diff, commit range, or file/directory path), use that target (if a committed file or directory path has no uncommitted diff, evaluate test coverage of its current contents).
   - If the input is omitted or only specifies a scope or custom instructions, infer the target heuristically using the current discussion and git state (`git status`/diff/branch):
     - If the active discussion focus and uncommitted working-tree changes point to different tasks, treat this as ambiguous and stop to ask before modifying test files.
     - Otherwise, prefer untested behaviors, review findings, failing checks, or recently implemented changes established in the current discussion when consistent with the working tree (isolating unrelated dirty changes).
     - Otherwise, if there are uncommitted changes (staged, unstaged, or relevant untracked files), target them—flagging and excluding unrelated dirty changes (and confirming first if staged and unstaged changes clearly belong to separate tasks).
     - Otherwise (clean working tree), if on a non-default branch with unmerged commits relative to the default branch (`merge-base..HEAD`), target those branch commits—confirming scope first if the branch is very large or spans multiple unrelated topics.
     - Otherwise (clean working tree on the default branch, or no divergence), fall back to `HEAD`.
   - Inspect acceptance criteria, non-goals, constraints, invariants, prior review findings, and custom instructions (if the target or expected behavior remains ambiguous, ask clarifying questions instead of guessing). Based on the project's existing test setup and the change's risk boundary, choose the lowest-cost layer (unit, integration, or E2E) where each behavior can be observed realistically without excessive mocking. Do not introduce a new test framework just to force a higher layer; if a behavior cannot be tested realistically without excessive mocking or a minimal production testability seam, report it as a testability gap with the minimal production change needed instead of mocking away the behavior or editing production code.
2. **Write discriminating tests**: Add or update tests following existing project conventions, avoiding duplicate tests for already-verified behavior. Cover discriminating inputs, control/invariant cases, boundary/error conditions, and minimal counterexamples—asserting observable outcomes or state rather than internal implementation details, so each test fails if the substantive behavior is removed or broken.
3. **Verify & diagnose**: Run the relevant test suites (and build/lint checks for touched test files). If a test fails, distinguish among three causes: (a) flawed test—fix the test; (b) real defect in production code—keep the failing regression test in place and report reproduction details instead of silently weakening assertions or modifying production code; (c) environment/dependency/setup blocker—do not misreport it as a production defect or leave a broken test; report it under local verification gaps.
4. **Report in plain engineering terms**: Lead with a clear, human-readable takeaway—what target scope was covered (noting any inferred scope or excluded unrelated changes), which real scenarios and failure modes are now protected, whether any test uncovered a production bug (with failing regression test details), and what still could not be verified locally or without production code changes. Then list the added/updated test files (with brief rationale for the chosen layer) and exact verification commands with observed results, avoiding internal prompt or workflow jargon.
5. **Boundaries**: Modify test files and test fixtures only; do not modify production code, commit, push, or perform destructive git/system actions unless explicitly requested. Preserve unrelated changes in the working tree, and clearly separate observed test results from static inferences.
