description: Add or strengthen discriminating tests at the right test layer without changing production code
argument-hint: "[target, scope, or custom instructions]"
---

Design, add, and run discriminating tests for the target changes, prioritizing any `unverified`, `add test`, or `failing` gaps from prior review and incorporating any custom instructions below.

Target, scope, or custom instructions (if omitted or no diff target is specified, default target is uncommitted changes—staged, unstaged, and relevant untracked files per `git status`—or `HEAD` if the working tree is clean): ${@:-default target}

1. **Identify gaps & choose test layer**: Determine the exact target via `git status`/diff (flagging unrelated dirty changes rather than folding them in; if a committed file or directory path is specified with no uncommitted diff, evaluate test coverage of its current contents). Inspect acceptance criteria, non-goals, constraints, invariants, prior review findings, and custom instructions (if the target or expected behavior is ambiguous, ask clarifying questions instead of guessing). Based on the project's existing test setup and the change's risk boundary, choose the lowest-cost layer (unit, integration, or E2E) where each behavior can be observed realistically without excessive mocking. Do not introduce a new test framework just to force a higher layer; if a behavior cannot be tested realistically without excessive mocking or a minimal production testability seam, report it as a testability gap with the minimal production change needed instead of mocking away the behavior or editing production code.
2. **Write discriminating tests**: Add or update tests following existing project conventions, avoiding duplicate tests for already-verified behavior. Cover discriminating inputs, control/invariant cases, boundary/error conditions, and minimal counterexamples—asserting observable outcomes or state rather than internal implementation details, so each test fails if the substantive behavior is removed or broken.
3. **Verify & diagnose**: Run the relevant test suites (and build/lint checks for touched test files). If a test fails, distinguish among three causes: (a) flawed test—fix the test; (b) real defect in production code—keep the failing regression test in place and report reproduction details instead of silently weakening assertions or modifying production code; (c) environment/dependency/setup blocker—do not misreport it as a production defect or leave a broken test; report it under local verification gaps.
4. **Report**: Summarize added/updated test files, the chosen test layer and rationale, what each case discriminates, exact verification commands and observed results, any failing regression tests intentionally left in place for production defects, and any testability or local verification gaps.
5. **Boundaries**: Modify test files and test fixtures only; do not modify production code, commit, push, or perform destructive git/system actions unless explicitly requested. Preserve unrelated changes in the working tree, and clearly separate observed test results from static inferences.
